# Bilingual EN/AR

How localisation works here, and the rules that keep the Arabic build from
degrading into an afterthought.

**Stack:** next-intl · App Router `[locale]` segment · ICU MessageFormat
**Locales:** `en` (default, unprefixed) · `ar` (`/ar/…`)
**Register:** Modern Standard Arabic (MSA), no diacritics
**Numerals:** Western (0-9) in both locales — the Gulf/UAE web convention

---

## The rule that governs everything

**The database stores English keys. The UI translates them.**

```
order.status = "PENDING"        ← database, always
"قيد الانتظار"                  ← UI, via messages/ar.json
```

Never translate a stored value. Indexes break, code starts branching on
translated strings, and English-locale users start seeing Arabic in their data.
Every enum gets a translation namespace instead — `orderStatus`,
`productStatus`, `roles`, `deliveryStatus`, and so on. There's a test asserting
every enum value in the Prisma schema has a translation in both catalogues.

The API returns English enums and IDs. Localisation happens on the client, so
responses stay cacheable and switching language needs no refetch.

## Adding a string

1. Add the key to **both** `messages/en.json` and `messages/ar.json`. A test
   fails on any key present in one and missing from the other — otherwise the
   missing locale renders the raw key (`counts.orders`) to users.
2. Use it: `const t = useTranslations('nav'); t('orders')`
3. Server components: `await getTranslations('nav')`, and call
   `setRequestLocale(locale)` first or the page silently opts into dynamic
   rendering.

### Counts need all six Arabic plural categories

Arabic distinguishes `zero`, `one`, `two`, `few` (3–10), `many` (11–99), and
`other`. English has two. Falling back to `other` reads wrong for most real
numbers.

```json
"products": "{count, plural, =0 {لا توجد منتجات} one {منتج واحد} two {منتجان} few {# منتجات} many {# منتجاً} other {# منتج}}"
```

A test asserts all six exist **and** that they produce genuinely different
strings — parity of form isn't enough if they were filled in mechanically.

## Layout: logical properties only

Never `ml-4`, `pl-2`, `left-0`, `text-left`, `border-l`, `rounded-l`.
Always `ms-4`, `ps-2`, `start-0`, `text-start`, `border-s`, `rounded-s`.

Flexbox and grid already respect `dir="rtl"` — don't override them.

**Legitimate exceptions**, content that is LTR regardless of UI language: code
blocks, phone/email/URL/password inputs, IBANs, card numbers. `globals.css`
applies `direction: ltr; unicode-bidi: isolate` to these via `.force-ltr` and
the relevant input types. Without isolation, a phone number inside an Arabic
sentence visually reorders and becomes genuinely unreadable, not just
misaligned.

---

## Icons: flip some, never all

`dir="rtl"` does **not** flip icons. Tag only the ones encoding direction with
`.icon-directional`:

| Flip | Don't flip |
|---|---|
| arrows, chevrons, back/forward | play, pause, skip *(physical tape motion)* |
| reply, send, external-link | clock, undo, redo, refresh *(time is linear)* |
| breadcrumb separators | checkmarks, X, warning, info |
| progress, pagination | search, pencil *(right-handed convention)* |
| carts, vehicles | logos, code brackets, hardware |

A blanket flip makes half the icon set wrong. A flipped play button points the
wrong way in every language.

## Animation: the silent breakage

**CSS transforms ignore `dir="rtl"`.** `translateX(-100%)` slides left in both
directions — so a drawer that enters correctly in English slides *off-screen* in
Arabic. Nothing errors.

Three fixes, in order of preference:

1. **Logical properties** — `inset-inline-start`, animated directly. Works both
   ways with no extra code.
2. **`:dir()` overrides** — when you need `transform` for compositor
   performance.
3. **Signed offsets in JS** — for GSAP: `lib/direction.ts` exposes
   `directionSign()` and `inlineOffset()`.

```ts
gsap.from(el, { x: inlineOffset('start', DISTANCE.lg) });
```

`Reveal` takes `from="start" | "end"`, not `"left" | "right"`. Physical values
are deliberately not offered — a hardcoded x-offset is exactly the bug this
prevents.

## Typography

Arabic glyphs render visually smaller than Latin at the same size, and the
script connects, so it needs more room:

- **Font:** IBM Plex Sans Arabic, loaded via `next/font` and selected by
  `html[lang='ar']`. Never rely on a Latin font's fallback — the result varies
  wildly by OS.
- **Size:** +6% (`font-size: 106.25%`)
- **Line-height:** 1.75 (vs ~1.5 for Latin)
- **No hyphenation** — Arabic doesn't hyphenate
- **No default underline** — it crosses the dots *below* ب ت ث ج ح خ and clips
  them, changing how words read. `globals.css` uses a `border-block-end` with
  padding instead.

---

## Testing RTL before translations exist

Force it on the English build to surface layout bugs early:

```html
<html lang="en" dir="rtl">
```

Every wrong-side icon and hardcoded `margin-left` appears immediately. Cheap
now, expensive after fifty components exist.

Lorem Ipsum doesn't stress RTL layout — use realistic Arabic ("أبو ظبي", long
form labels) to catch text expansion and font fallback problems.

## What's covered by tests

- Catalogue parity — no key in one locale and not the other
- No empty strings, no untranslated copies of English
- Every Prisma enum has translations in both locales
- All six Arabic plural categories, producing distinct output
- Every ICU message parses (a malformed one throws at *render* time)
- `getDirection` for ar/he/fa/ur, and unknown locales falling back to LTR
- `directionSign` / `inlineOffset` mirroring correctly — mutation-verified

## Not done yet

- Playwright screenshot diffing in both directions
- `Intl.Collator` sorting for Arabic strings — needed once tables sort by name;
  default `<`/`>` gives Unicode codepoint order, which is not alphabetical
- Server-rendered emails in the user's locale (no email transport yet)
- **Native review.** These translations are unreviewed MSA. Worth a pass before
  anything client-facing ships.
